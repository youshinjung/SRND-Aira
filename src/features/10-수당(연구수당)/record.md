# 기능 화면 기록

> 실제 SRnD 화면을 2회 반복해서 확인했습니다(2026-08-28). 팝업의 전체 필드 레이아웃은 두 번 모두 동일하게 재현되어 구조는 신뢰도 높음. 다만 자동 클릭기록 스크립트가 이 팝업의 iframe 구조를 못 잡아서, 팝업을 여는 앞단계(비목 선택 팝업, 실사용자 검색 팝업, 참여연구원 불러오기 팝업의 내부 구조)는 아직 못 봤습니다 — 해당 부분은 "미확인"으로 표시.

## 기본 정보

- 기능 번호: 10
- 기능명: 수당(연구수당)
- 교육영상: https://youtu.be/iDYAPYg_rOk
- SRnD 메뉴 경로 (실제 화면 확인): 연구관리 > 내과제관리 > (연구활성화사업 그룹) > `지출신청(연구자용)`
  - 같은 메뉴 그룹에 `기여도신청`이라는 별도 메뉴가 존재함. 아래 "신규 발견" 절 참고 — 19-2 기여도평가서 데이터가 이 메뉴에서 먼저 등록되고, 여기서 "불러오기" 하는 구조로 추정됨(미확인, 다음 조사 때 `기여도신청` 메뉴 자체를 열어봐야 함).
- 팝업 화면명: `수당 지급신청` (팝업 타이틀바 텍스트로 확인)
- 화면 ID: 미확인 (목록 화면 `지출신청현황`의 화면ID는 `FASMLGE001E`였으나, 이건 목록 화면이고 `수당 지급신청` 팝업 자체의 화면ID는 아직 못 봄)
- 기록일: 2026-08-28

## 사전 조건

- 필요한 권한: 연구자 계정, 해당 과제 참여연구원 권한
- 사용자가 직접 완료할 로그인·계정전환: 로그인, 위임계정 전환 (오늘 완료함)

## 클릭 순서

**영상 기준 흐름** (실제 화면과 아래 "실제 화면에서 확인된 구조"로 재해석 필요):

1. `지출신청(연구자용)` 메뉴 진입
2. 검색조건에 과제번호 입력 → `조회` 버튼 클릭
3. 조회 결과 우측 지출구분 중 `수당` 란 체크 → `수당 지급신청` 팝업 호출
4. 팝업 내 청구정보 입력 (주황색 셀 = 필수값 — 실제 화면에서도 주황 테두리로 확인됨: 세목/비용, 실사용자, 제목, 연구수당평가기간)
5. 팝업 상단 버튼: `저장` / `삭제` / `신청` / `신청취소` / `사용내역서 출력` / `사용내역서 자동첨부` — **`저장`·`삭제`·`신청`·`신청취소`는 모두 상태를 확정/변경하는 동작이라 자동화 금지 대상으로 취급**(SECURITY.md의 "삭제·취소 확정" 금지 조항에 `신청취소`도 해당한다고 판단)
6. 팝업 닫고 검색 결과로 복귀 → 방금 입력한 연구수당 지급란 체크 → `청구` 버튼 클릭 ← **최종 처리, 자동화 금지** (영상 기준, 실제 화면 미확인)
7. (연구자 작업 범위 밖) 이후 결의는 관리기관 담당자가 기한·내부결재로 진행

## ⚠️ 신규 발견: "수당 지급신청" 팝업은 참여연구원 1명 기준일 가능성

영상 대본은 "팝업 하나에 참여연구원 여러 명의 기여도를 각각 입력"하는 것처럼 설명하지만, 실제 화면 구조를 보면 다음 필드가 전부 **단수(1건)**로 보입니다.

- `실사용자` 필드: 사번 1개 + 이름 1개 (돋보기로 검색해서 채우는 단일 필드)
- `신청금액` 필드: 금액 1개 (표가 아니라 단일 입력칸)
- `지출대상자 지급내역` 표: 좌우 끝까지 스크롤해서 전체 컬럼을 확인했는데 **성명·직급·기여도·지급액 컬럼이 없고**, `비과세·소득세·주민세·[개인 4대보험 4종]·[기관 4대보험/산재보험 5종]·퇴직적립금`만 있음 → 이 표는 "실사용자 1명"의 세금·4대보험 원천징수 내역을 자동 계산해서 보여주는 표로 보임 (참여연구원 여러 명의 기여도를 나열하는 표가 아님)
- `개인지급내역` 표(하단)도 1행만 존재 (`실사용자`와 동일 인물)

**추정**: 참여연구원별 기여도(%)와 지급액은 이 팝업이 아니라 별도 메뉴 `기여도신청`(19-2 기여도평가서에 해당)에서 먼저 등록해두고, 여기 팝업 상단의 `기여도신청불러오기` 검색창으로 그 건을 불러와 연결하는 구조로 보임. 그렇다면 **연구수당 청구는 참여연구원 수만큼 이 팝업을 반복해서 각각 만들어야 할 가능성**이 있습니다.

→ **다음 조사 때 반드시 확인**: ① `기여도신청` 메뉴를 열어서 19-2 서식과 매칭되는 화면인지, 성명별 기여도 입력 UI가 거기 있는지 확인. ② `수당 지급신청` 팝업의 `기여도신청불러오기`에 실제 검색어를 넣어 어떤 결과가 뜨는지 확인 (돋보기 버튼 옆 텍스트박스 — 아직 미사용).

## 첨부파일(증빙) 요구사항 — UI 구현 시 참고용

교육영상 대본과 사용자 제공 서식(`19-1`, `19-2`, 부당집행계산식.xlsx)을 근거로 정리한 내용입니다. 실제 파일첨부 UI를 열어보지 못했으므로, 자동화(`fill.js`) 구현 시에는 아래 내용을 "사용자가 준비해서 직접 첨부하는 항목"으로 다루고 자동 업로드 대상으로 만들지 말 것.

| 문서 | 첨부 대상 여부 | 근거 |
|---|---|---|
| **연구수당 기여도 평가서** (19-2 서식 기준, 실제 작성·서명 완료본) | **필수 첨부** | 영상 대본: "연구 수당은 방금 입력한 기여도에 대한 기여도 평가서 증빙이 필수이므로 반드시 하단의 파일첨부 안에 업로드하여 주시기 바랍니다" |
| 연구비지급신청서/연구수당 지급 신청서 (19-1 서식) | 첨부 대상 아닌 것으로 보임 | 영상에서 별도 첨부 언급 없음. 이 서식 내용 자체가 SRnD 온라인 입력(팝업의 예산정보·수당기본정보·지급내역)으로 대체되는 것으로 추정. **확인 필요**: 기관에 따라 결재용으로 별도 첨부를 요구할 수도 있으니 실제 화면에서 파일첨부 안내문구·필수여부 표시를 다시 확인할 것 |
| 부당집행 기준 안내 및 계산식.xlsx | 첨부 대상 아님 | 연구자용 자체 점검 도구. SRnD 화면 항목이 아님 |

**요약**: 파일첨부 슬롯에는 최소 "기여도 평가서"(19-2 양식에 실제 값 채운 문서, 보통 PDF/스캔본) 1개는 반드시 들어가야 신청 가능한 것으로 보임. UI에서 "필수 첨부 파일이 없으면 신청 불가" 같은 검증이 있을 가능성이 높으므로, `fill.js`는 파일이 준비되지 않았으면 첨부 단계에서 멈추고 사용자에게 안내해야 함.

`extract.js`가 입력 문서에서 추출해야 할 스키마의 기준이 되는 서식 3종을 검토했습니다. 이 서식들은 SRnD 화면과 별개의 신청서 양식이며, 실제 필드명·구조는 확인됐지만 SRnD 화면 상의 실제 컴포넌트명과는 다를 수 있으므로 화면 기록으로 교차검증이 필요합니다.

### 19-1. 연구비지급신청서 / 연구수당 지급 신청서 (붙임 5)

**1. 해당 과제내역**: 과제번호, 연구책임자 성명, 연구책임자 직급, 연구과제명, 연구기간(시작~종료), 평가기간(시작~종료), 지원기관명, 연구비

**2. 지급내역 표** (참여연구원별 행 반복):
| 열 | 의미 |
|---|---|
| 직급 | |

### 19-2. 연구수당 기여도 평가서 (붙임 5-1)

**1. 일반사항**: 과제번호, 연구책임자, 연구기간, 평가기간, 연구수당 총 예산, 금번 지급 예산

**2. 평가 내용 표**: 평가항목(연구과제 수행/연구결과물/연구결과 발표/기타 — 과제별로 수정 가능) × 참여연구원별 평가점수. 평가항목별 배점 합계는 100점 고정. 참여연구원별 "금번 지급액에 대한 기여도(%)" = 참여연구원 평가점수 총합 × (금번 지급 예산 / 연구수당 총예산)

→ 이 기여도(%)가 19-1 지급내역 표의 "기여도(B)"로 그대로 연결됨. 즉 **기여도는 기여도 평가서에서 산출되어 지급신청서로 옮겨지는 값**이라 자동화 시 두 문서/화면 간 정합성 검증이 필요. (위 "신규 발견" 절에서 추정한 `기여도신청` 메뉴가 바로 이 문서의 디지털 버전일 가능성이 높음)

### 연구수당-부당집행 기준 안내 및 계산식.xlsx (참고용, 검증 로직 힌트)

SRnD 화면 항목은 아니지만 연구자가 스스로 부당집행 여부를 점검하는 계산식 시트. 핵심 로직:

- 연구수당 집행비율 = 연구수당 집행액 / 연구수당 계상액 × 100
- (이월금 포함) 직접비 집행비율 = (직접비 집행액 + 전년도 이월금 중 직접비 집행액) / 직접비 계상액 × 100
- **위반 조건**: 연구수당 집행비율 − 직접비 집행비율 > 20%p 이면 초과분만큼 반납액 발생 (`연구수당 계상액 × (연구수당집행비율% − 직접비집행비율% − 20%)`)

→ `extract.js`에서 연구수당 신청 전 이 비율을 계산해 사용자에게 경고(반납 위험)해주는 것이 유용할 수 있음. 단, 화면 기록이 아직 부족해 지금 코드화하지 않고 record.md에만 남겨둠.
